개인 콘텐츠 채널의 발행 상태 관리 도구. 발행 여부를 사람 기억에 의존하다가
오판·중복 노출 사고가 나서, 상태를 시스템이 들게 만들었습니다.

## 문제 정의

콘텐츠를 혼자 기획하고 만들고 올리다 보면, 각 에피소드가 지금 어느 단계에 있는지를
결국 머릿속에서만 관리하게 됩니다. 소재를 모아둔 곳, 대본을 쓴 곳, 실제로 올린 곳이
전부 흩어져 있으니 "이건 올렸던가?"를 판단할 근거가 기억밖에 없습니다.

그러다 사고가 났습니다.

- **오판**: 제작만 해두고 발행하지 않은 건을 발행했다고 착각해 그대로 묻어버림
- **중복 노출**: 이미 다룬 소재를 다시 다뤄서 같은 내용을 두 번 내보냄
- **취소 이력 증발**: 발행을 접은 건에 대해 왜 접었는지가 남지 않아, 나중에 같은 판단을 반복

세 가지 모두 원인이 같습니다. **상태를 사람이 들고 있었다는 것.**

그래서 이 도구는 기능을 늘리는 대신 딱 하나만 합니다.
에피소드의 상태와 그 근거를 시스템에 기록하고, 판단은 기록을 보고 하게 만드는 것.

## 데이터 모델

### Episode — 발행 단위 콘텐츠 1건

| 필드 | 설명 |
|---|---|
| `number` | 에피소드 번호 (고유) |
| `title` | 제목 |
| `category` | AI소식 / 두드려봄 / 기회 / 꿀팁 |
| `status` | 제작중 / 제작완료 / 발행완료 / 발행취소 |
| `published_at` | 발행일 (미발행 시 비어 있음) |
| `cancel_reason` | 취소사유 (취소 건이 아니면 비어 있음) |
| `created_at` | 생성일시 |

`status`가 이 프로젝트의 핵심입니다. **제작완료와 발행완료를 분리한 것**이 의도적인
설계인데, 오판 사고가 정확히 이 둘을 뭉뚱그린 데서 나왔기 때문입니다. 만들어 둔 것과
내보낸 것은 다른 상태이고, 시스템은 이 둘을 절대 같은 칸에 두지 않습니다.
`cancel_reason`도 같은 이유로 존재합니다. 접었다는 사실만으로는 다음 판단에
도움이 되지 않고, 왜 접었는지가 남아야 같은 소재를 다시 집어들 때 근거가 됩니다.

### Source — 에피소드의 근거가 되는 원본 자료

| 필드 | 설명 |
|---|---|
| `url` | 원본 URL |
| `collected_at` | 수집일시 |
| `summary` | 요약 |
| `episode` | 연결된 에피소드 (아직 없으면 비어 있음) |

소재는 에피소드보다 먼저 쌓입니다. 그래서 `episode`는 nullable입니다.
아직 어디에도 쓰지 않은 소재가 정상 상태이고, 나중에 에피소드가 만들어질 때 연결됩니다.
중복 노출을 막을 근거가 바로 이 테이블에 쌓입니다. 이미 어떤 URL을 다뤘는지가
기록으로 남아야 "이거 전에 했던 건가?"를 기억이 아니라 조회로 답할 수 있습니다.

### Deadline — 마감이 있는 기회 정보

| 필드 | 설명 |
|---|---|
| `title` | 제목 |
| `due_date` | 마감일 |
| `official_url` | 공식링크 |
| `episode` | 연결된 에피소드 (아직 없으면 비어 있음) |

'기회' 카테고리는 다른 카테고리와 성질이 다릅니다. 늦으면 가치가 0이 됩니다.
그래서 마감일을 별도 모델로 분리했습니다. 아직 에피소드로 만들지 않은 마감 건도
독립적으로 추적되어야 하므로 여기서도 `episode`는 nullable입니다.

## 로드맵

상태를 기록할 그릇을 먼저 만들고, 그 위에 판단을 얹는 순서로 갑니다.
지금까지 그릇 쪽 두 가지가 끝났고, 중복 감지부터가 남은 일입니다.

**완료 — 발행 상태 전이 검증**

`제작중 → 제작완료 → 발행완료` 순방향만 허용하고, 발행취소는 제작완료에서만
가능합니다. 발행완료에는 발행일이, 발행취소에는 취소사유가 없으면 전이가 막힙니다.
오판 사고의 원인이 상태 칸이 아무렇게나 바뀔 수 있었다는 데 있었기 때문에,
기록의 신뢰도를 여기서 먼저 확보했습니다.

**완료 — 마감 D-day 계산**

`Deadline`의 남은 일수를 저장하지 않고 조회 시점에 계산합니다.
`days_left` · `is_expired` · `d_day_label`(`D-18` / `D-DAY` / `마감`)을 제공하고,
`Deadline.objects.active()`로 미마감 건만 급한 순서대로 가져옵니다.

D-day를 컬럼으로 저장하지 않은 이유는 날짜가 지나면 곧바로 틀린 값이 되기 때문입니다.
저장된 D-day는 갱신을 누가 책임지느냐는 문제를 새로 만들고, 그건 이 프로젝트가
없애려는 바로 그 종류의 문제입니다. 기준일은 `settings.TIME_ZONE`(Asia/Seoul)이며,
UTC로 계산하면 한국 시간 자정부터 오전 9시 사이에 하루가 어긋납니다.

**1단계 — 중복 감지**

새 소재를 넣을 때 기존 `Source`와 겹치는지 알려줍니다.
URL 정규화 후 완전 일치 검사부터 시작하고, 그다음 제목·요약 기반 유사도 검사를 붙입니다.
규칙 기반이라 오탐이 있겠지만, 아무 경고도 없는 지금보다는 확실히 낫습니다.

**2단계 — 로컬 LLM 판정**

URL이 달라도 같은 사건을 다루는 경우는 문자열 비교로 잡히지 않습니다.
여기서부터 LLM이 필요합니다. 소재 요약과 기존 에피소드를 비교해
"실질적으로 같은 내용인가"를 판정하게 합니다.

로컬에서 돌리는 것이 전제입니다. 아직 발행하지 않은 기획이 외부 API로 나가는 것이
껄끄럽고, 매번 소재를 넣을 때마다 호출되는 성격이라 비용도 맞지 않습니다.

**판정은 어디까지나 참고용입니다.** LLM이 상태를 바꾸지는 않습니다.
경고를 띄우고 최종 결정은 사람이 합니다. 애초에 이 프로젝트의 목적이
판단을 자동화하는 게 아니라, 판단할 근거를 기억 밖에 두는 것이기 때문입니다.

## 시작하기

```bash
python -m venv venv
venv\Scripts\activate          # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt

copy .env.example .env         # macOS/Linux: cp .env.example .env
# .env를 열어 DJANGO_SECRET_KEY 값을 채웁니다.
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"

python manage.py migrate
python manage.py loaddata initial_episodes    # ep1~10 실데이터 시드 (선택)
python manage.py createsuperuser
python manage.py runserver
```

`http://127.0.0.1:8000/admin/` 에서 세 모델을 모두 다룰 수 있습니다.

비밀값은 전부 `.env`로 관리하며 코드에 하드코딩하지 않습니다.
`.env`는 커밋되지 않고, `.env.example`만 저장소에 포함됩니다.

## 기술 스택

Django 6.1 · SQLite · Python 3.14

혼자 쓰는 도구이고 데이터도 많지 않아 SQLite로 시작합니다.
DB를 바꿔야 할 이유가 실제로 생기기 전까지는 바꾸지 않습니다.
